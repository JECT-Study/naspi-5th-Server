# 스토리 완료 조건 검증

대상: `$ARGUMENTS` (비어 있으면 현재 브랜치의 Jira 키)

이 스킬은 **검증과 보고만** 한다. 코드, 테스트, 문서(체크박스 포함)를 수정하지 않는다.

## 1. 스토리 찾기

```
scripts/find-story.sh $ARGUMENTS
```

- 종료 코드 1 또는 2이면 출력된 메시지를 그대로 전달하고 멈춘다. (Jira 키가 `docs/issues`의 `- Jira:` 칸에 기재되지 않은 경우 등)
- 출력의 `FILE` 줄에서 스토리 위치를, 본문에서 다음을 뽑는다.
  - 완료 조건 (`- [ ]` / `- [x]` 항목)
  - 정책 링크 (`정책:` 줄) → 링크된 `docs/policies/<버전>/domain/*.md` 섹션을 읽는다 (버전은 스토리 파일 경로의 `docs/issues/<버전>/`).
  - 결정 필요 항목
  - 선행 스토리

## 2. 검증 기준 만들기

- 완료 조건 각각을 검증 항목으로 둔다.
- 링크된 정책 섹션의 규칙 중 완료 조건에 빠진 것이 있으면 `[정책]` 항목으로 추가한다. (완료 조건이 정책을 다 옮기지 못했을 수 있다)
- `결정 필요` 항목은 검증 대상이 아니라 별도로 나열한다.

## 3. 변경 범위 파악

```
git merge-base HEAD origin/development/1.0.0
git diff --stat <merge-base>...HEAD
git status --short
```

커밋된 변경, 아직 커밋하지 않은 변경, 새 파일을 모두 포함한다. 변경 범위 밖에 이미 구현돼 있을 수도 있으므로, 항목별 검색은 저장소 전체를 대상으로 한다. 단, 근거로 든 코드가 이번 브랜치 변경분인지 기존 코드인지 구분해 표시한다.

## 4. 항목별 근거 찾기

각 검증 항목마다 다음을 찾는다.

- **구현 근거**: 규칙이 실제로 강제되는 코드 위치 (`파일:줄`). 메서드 이름만 비슷한 것은 근거가 아니다. 조건문, 검증 로직, 제약(유니크 등)을 직접 확인한다.
- **테스트 근거**: 그 규칙을 검증하는 테스트 (`테스트클래스#메서드` 또는 `@DisplayName`). 경계값(최대 길이, 0, 정확히 경계인 시각 등)이 정책에 있으면 경계값 테스트가 있는지도 본다.

판정:

| 판정 | 기준 |
|---|---|
| ✅ 충족 | 구현 근거와 테스트 근거가 모두 있다 |
| 🟡 테스트 없음 | 구현은 확인했지만 이를 검증하는 테스트가 없다 |
| ❌ 미구현 | 구현 근거를 찾지 못했다 |
| ❓ 판단 불가 | 정책이 모호하거나 `결정 필요` 항목에 걸려 판정할 수 없다 |

근거를 찾지 못하면 추측으로 ✅를 주지 않는다. 확신이 없으면 🟡나 ❓로 두고 이유를 적는다.

## 5. 테스트 실행

4에서 근거로 든 테스트 클래스만 실행한다.

```
./gradlew test --tests "<클래스 FQCN>" [--tests ...] -q
```

실패한 테스트가 있으면 해당 항목의 판정을 ❌로 내리고 실패 내용을 적는다.

## 6. 리포트

다음 형식으로 보고한다.

```
## 스토리 검증: <스토리 ID> <스토리 문장> (<Jira 키>)
위치: <FILE 경로:줄> · 브랜치: <브랜치> · 테스트 실행: <통과 n / 실패 n>

| # | 검증 항목 | 판정 | 구현 근거 | 테스트 근거 |
|---|---|---|---|---|
| 1 | <완료 조건> | ✅ | `파일:줄` | `Test#method` |
| 2 | [정책] <완료 조건에 없던 정책 규칙> | 🟡 | ... | - |

### 남은 작업
- ❌, 🟡 항목별로 무엇이 필요한지 한 줄씩

### 결정 필요 (검증 제외)
- 스토리의 결정 필요 항목

### 선행 스토리
- 선행 스토리 ID와, 그 스토리가 필요로 하는 코드가 존재하는지 여부
```

마지막에 모든 항목이 ✅이면 "완료 조건 체크박스를 [x]로 바꿀까요?"라고 묻는다. 사용자가 동의할 때만 체크박스를 수정한다.
