# Kafka 도입 설계 (검토안)

> 상태: **제안 / 미승인**. 학습 목적으로 Kafka를 도입할 때의 설계안이다.
> 새 라이브러리·기술 스택 도입은 CLAUDE.md 규칙상 팀 승인 후 진행한다 (`spring-kafka`, 로컬 docker Kafka, Testcontainers, k8s 배포).
> 정책 기준: [docs/policies/v1](../policies/v1) — 이 문서와 정책서가 어긋나면 정책서가 기준이다.

## 1. 요약

| 영역 | Kafka 사용 | Kafka의 역할 |
|---|---|---|
| 리그 시작 → 자산 배분·시세 초기화 | **사용 안 함** | — (원자성 필요, Spring 동기 이벤트) |
| 주문 접수·취소·만료 → 매칭 | 사용 (학습 핵심) | 종목별 순서 정렬 (시퀀서) |
| 체결 → 화면 발행 | 사용 가능 | 커밋 후 알림 |
| 공시 게시 → AI 뉴스 생성 | 사용 (가장 적합) | 비동기 작업 큐 + 재시도 |
| 공시 작성, 댓글, 반응 | 사용 안 함 | — (동기 CRUD) |

판단 기준: **같은 트랜잭션으로 묶여야 하는 일은 Kafka를 거치지 않는다.** Kafka는 DB 트랜잭션과 함께 원자적으로 커밋될 수 없다.

## 2. Kafka를 쓰지 않는 곳: 리그 시작

리그 시작 시 `league`가 `LeagueStarted`를 발행하고 `market`(시초가·최초 기준가), `asset`(초기 자산 배분)이 구독한다.

- 정책: "모든 사용자의 자산 배분이 완료된 동일한 시장 상태에서 거래 개시", AST-01 "배분은 원자적으로 처리"
- Spring 동기 `@EventListener`는 발행 메서드와 **같은 스레드·같은 트랜잭션**에서 실행되므로, 리스너 하나라도 실패하면 리그 시작 전체가 롤백된다.
- Kafka로 바꾸면 DB 커밋과 메시지 발행·소비 사이에 틈이 생겨 "시작됐지만 배분 안 된" 상태가 생긴다. 이를 막으려면 Outbox + Inbox + Saga(`배분중` 상태, 완료·실패 이벤트, 보상 처리)가 필요하다. 모든 모듈이 같은 DB를 쓰는 지금 구조에서는 얻는 것이 없다.

같은 트랜잭션이 깨지는 경우 (주의):
- 리스너에 `@Async`, `REQUIRES_NEW` 사용
- 리스너가 예외를 잡아서 삼킴
- `@TransactionalEventListener` 기본값(`AFTER_COMMIT`) 사용
- 리스너를 다른 스레드에서 실행 (가상 스레드 여부와 무관, **스레드가 바뀌면** 트랜잭션이 끊김)

## 3. 주문·체결

### 3.1 전체 흐름

```
[주문 API] ─(직접 호출)→ asset: 현금·주식 예약
     │
     └─ outbox → [order-commands, key=종목 ID] → [매칭 컨슈머]
                                                   │
                         ┌─(직접 호출)→ asset:  매수자·매도자 정산, 예약 해제
                         ├─(직접 호출)→ market: 현재가·거래량 갱신
                         └─ outbox → [trade-executed] → websocket
```

| 단계 | Publish | Subscribe |
|---|---|---|
| 주문 접수 / 취소 / 미체결 만료 | order | order (매칭 컨슈머) |
| 체결 완료 | order (매칭 컨슈머) | websocket (호가창·체결가·차트·내 자산·체결 알림) |

- `order-commands`는 pub·sub이 모두 order다. 다른 도메인에 알리는 용도가 아니라 **같은 종목의 주문을 한 줄로 세우는 시퀀서**다.
- asset 정산과 market 현재가 갱신은 Kafka를 거치지 않고 매칭 트랜잭션 안에서 직접 호출한다 (`order → asset → market` 방향, 순환 없음).
  - 정산이 비동기면 이미 판 주식을 다시 팔 수 있는 틈이 생긴다.
  - 현재가가 비동기면 09:00 거래일 전환 시 종가·기준가가 어긋날 수 있다.

### 3.2 Kafka 대신 쓸 수 있는 방법

같은 종목을 한 번에 하나씩 처리하는 것이 핵심이다. 실제 필요만 보면 DB 비관적 락으로 충분하다.

| 방법 | 장점 | 단점 |
|---|---|---|
| DB 비관적 락 (`SELECT ... FOR UPDATE`) | 가장 단순, 응답에 체결 결과 포함, 다중 서버 동작 | 같은 종목 주문이 몰리면 락 대기 |
| 메모리 큐 (종목별 단일 스레드) | 빠름 | 단일 서버 전제, 재시작 시 유실 |
| Kafka 시퀀서 | 락 없이 순서 보장, 주문 로그 재처리, 버스트 흡수, 매칭 확장 | 비동기 응답, outbox·멱등 처리·운영 부담 |

학습 순서 제안: DB 락으로 먼저 구현 → `trade-executed`만 Kafka로 발행 → `order-commands` 시퀀서로 전환.

### 3.3 주문 접수 (보내는 쪽)

1. 하나의 DB 트랜잭션에서
   - 검증: 리그 거래 중, 100원 호가 단위, 상·하한가, 수량
   - asset 직접 호출로 예약 (부족하면 즉시 거절)
   - 주문 저장 (상태 `접수`)
   - outbox 저장
   - 응답: 주문 ID와 `접수` (체결 결과는 WebSocket)
2. outbox 릴레이가 미발송 행을 ID 순서로 읽어 발행, ack 후 `보냄` 표시
   - 프로듀서: `acks=all`, `enable.idempotence=true`
   - 릴레이는 1개만 실행
   - 학습 초기에는 `@TransactionalEventListener(AFTER_COMMIT)` + `KafkaTemplate.send`로 단순화 가능 (커밋 직후 장애 시 유실 가능)

메시지:

| 항목 | 값 |
|---|---|
| 토픽 | `order-commands` (접수·취소·만료를 한 토픽에) |
| 키 | 종목 ID |
| 값 | `{commandId, type: PLACE/CANCEL/EXPIRE, orderId}` — 상세는 DB에서 읽음 |
| 파티션 수 | 처음에 정하고 바꾸지 않음 (예: 6~12) |

### 3.4 매칭 (받는 쪽)

- `@KafkaListener(topics = "order-commands", groupId = "order-matching")`
- `enable.auto.commit=false`, DB 커밋 후 offset 커밋
- `concurrency` ≤ 파티션 수, 컨슈머 안에서 다른 스레드로 넘기지 않음

메시지 1건 = DB 트랜잭션 1개:
1. `orderId`로 주문 조회
2. 멱등 확인: 상태가 `접수`가 아니면 건너뜀
3. 반대편 대기 주문을 가격·시간 우선으로 매칭
4. 체결 저장, 양쪽 잔량·상태 갱신
5. asset 정산, market 현재가·거래량 갱신
6. outbox에 `TradeExecuted` 저장

실패: `DefaultErrorHandler`로 재시도 → DLT. DLT로 간 주문은 `거절` 처리하고 예약 해제.

### 3.5 매칭 규칙 (정책: order.md 체결)

정렬:
- 매도: 낮은 가격 → 먼저 접수
- 매수: 높은 가격 → 먼저 접수

매수 지정가가 들어왔을 때 (매도는 방향만 반대):
```
반복:
  ① 최우선 매도 주문을 꺼낸다
  ② 없거나 매도가 > 매수가 → 멈춤                (매수가 ≥ 매도가일 때 체결)
  ③ 상대가 내 주문 → 내 잔량 취소, 멈춤           (자전거래 금지: 신규 주문 잔량 취소)
  ④ 수량 = min(내 잔량, 상대 잔량), 가격 = 상대(대기 주문) 가격
  ⑤ 체결 저장, 잔량 차감, 정산
  ⑥ 내 잔량 0 → 멈춤, 아니면 ①
멈춘 뒤: 지정가는 잔량 대기, 시장가는 잔량 취소
```

예시: 매도 A 10,000×30(09:01), B 10,000×50(09:03), C 10,200×40(09:02) 대기 중 매수 지정가 10,200×100 진입

| 순서 | 상대 | 체결가 | 수량 | 내 잔량 |
|---|---|---|---|---|
| 1 | A | 10,000 | 30 | 70 |
| 2 | B | 10,000 | 50 | 20 |
| 3 | C | 10,200 | 20 | 0 |

예약 1,020,000원 − 체결 1,004,000원 = 16,000원 예약 해제.

시장가: 보호 가격(매수 = 최우선 매도 × 105%, 매도 = 최우선 매수 × 95%, 상·하한가와 100원 단위 적용)을 한도로 한 지정가처럼 처리하고 잔량 취소. 상대 호가가 없으면 전량 취소.

- 보호 가격은 **API 접수 시 계산해 주문에 저장**한다 (정책 "주문 접수 시 최우선 상대 호가 기준", 예약 금액도 이 값 사용). 컨슈머는 저장된 값을 한도로 쓴다.
- 자사주 매도는 체결 시에도 최소 유지분 1,000주 확인 (asset).

### 3.6 순서 보장

| 순서 | 담당 |
|---|---|
| 가격 우선 | 호가창 정렬 (Kafka 무관) |
| 시간 우선 | Kafka 파티션 도착 순서 |
| 접수·취소·만료 처리 순서 | Kafka 파티션 순서 |

파티션 순서 유지 조건:
1. 키 = 종목 ID
2. 프로듀서 `enable.idempotence=true` (`max.in.flight.requests.per.connection` ≤ 5)
3. 파티션당 컨슈머 스레드 1개, 컨슈머 내부 비동기 처리 금지
4. 파티션 수 고정

함정:
- **outbox ID 순서 ≠ 커밋 순서.** 트랜잭션 A(ID 10)보다 B(ID 11)가 먼저 커밋되면 11이 먼저 발행된다. → "접수 순서"를 **Kafka 도착 순서**로 정의하고, 컨슈머가 처리할 때 접수 순번(`seq`)을 부여한다. 호가창 시간 우선은 `주문일시`가 아니라 `seq`로 정한다.
- **09:00 만료와 새 주문이 섞임.** 만료 명령은 메시지 위치가 아니라 "이전 거래일 주문"을 만료시킨다 (주문은 접수 시 거래일이 정해짐).
- **리밸런싱 시 재전달.** 커밋 안 된 offset은 다시 온다 → 멱등 처리.

### 3.7 호가창 자료구조

방법 1: DB 조회 (추천 시작점)
```sql
-- 매수 진입 시
SELECT * FROM orders
WHERE stock_id = ? AND side = 'SELL' AND status IN ('미체결', '부분체결')
ORDER BY price ASC, seq ASC;
-- 매도 진입 시: side = 'BUY' ORDER BY price DESC, seq ASC
```
인덱스 `(stock_id, side, status, price, seq)`. DB가 유일한 기준이라 복구가 필요 없다.

방법 2: 메모리 (거래소 방식)
```java
TreeMap<Long, ArrayDeque<Order>> asks = new TreeMap<>();                           // 낮은 가격 우선
TreeMap<Long, ArrayDeque<Order>> bids = new TreeMap<>(Comparator.reverseOrder()); // 높은 가격 우선
Map<Long, Order> byId = new HashMap<>();                                           // 취소용
```
- 가격 수가 작다: ±30%, 100원 단위 → 기준가 10,000원이면 7,000~13,000원 61개. 거래일마다 다시 만드는 배열도 가능.
- 파티션 할당 시(시작·리밸런싱) DB에서 재구성
- 메모리는 DB 커밋 성공 후 반영, 실패 시 해당 종목 재구성
- 파티션당 스레드 1개라 락 불필요

`OrderBook` 인터페이스 뒤에 두고 DB 구현 → 메모리 구현 순으로 교체.

## 4. 공시 → AI 뉴스

정책이 비동기·재시도를 전제로 쓰여 있어 가장 잘 맞는다 (contents.md, CNT-05, CNT-06, ERD `news.생성상태`·`재시도횟수`).

```
공시 작성 API: DB 트랜잭션 { 공시 저장, outbox } → 응답
      ↓
[disclosure-published] → 뉴스 생성 컨슈머 (contents)
   성공 → 뉴스 저장 (생성상태=완료, 호재/악재)
   실패 → retry-1 → retry-2 → DLT → 생성상태=실패 → 수동 재시도 버튼
```

| 정책 | 구현 |
|---|---|
| 자동 재시도 최대 2회 | `@RetryableTopic(attempts = 3)` + backoff |
| 자동 재시도 모두 실패 시 수동 재시도 | DLT 처리에서 `생성상태 = 실패` 저장 |
| 수동 재생성에도 자동 재시도 2회 | 수동 재시도 API가 같은 토픽에 재발행 |
| 실패해도 공시 원문 유지 | 공시 저장과 뉴스 생성 분리 |
| 공시 삭제 후에도 자동 재시도 실행, 수동 재시도 불가 | 컨슈머는 삭제 여부 확인 안 함, 수동 재시도 API에서 차단 |

- 순서 무관 → 키 = 공시 ID, 병렬 처리 가능
- 중복 방지: `news.공시id` 유니크 (공시 1건당 뉴스 1개)
- "말이 되는 문장 없음 → 미생성"은 예외로 던지지 않음 (재시도 대상 아님) — CNT-05 결정 필요
- AI 요청 제한은 `concurrency`로 조절
- AI 제공자 미정 → 초기에는 stub

## 5. 주문 vs 뉴스

| | 주문 (`order-commands`) | 뉴스 (`disclosure-published`) |
|---|---|---|
| 역할 | 시퀀서 | 작업 큐 + 재시도 |
| 순서 | 필수 | 불필요 |
| 실패 | 거절 + 예약 해제 | 재시도 2회 → DLT → 수동 재시도 |
| 학습 포인트 | 파티션 키, offset, 멱등 처리, outbox | `@RetryableTopic`, DLT, backoff |

시작하기 쉬운 쪽은 뉴스다 (순서 무관, 실패해도 공시에 영향 없음).
