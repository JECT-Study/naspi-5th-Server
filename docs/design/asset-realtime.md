# 내 자산 실시간 발행 설계

> 대상 스토리: [AST-02](../issues/v1/asset.md#ast-02-참여자는-자신의-현금-보유-주식-예약-자산-총자산을-조회할-수-있다) (ND-10)
> 정책: [asset.md#자산-조회](../policies/v1/domain/asset.md#자산-조회)
> 상태: 설계 확정 (2026-11-12 개정: 현재가 캐시, 변경된 리그만 주기 발행), 구현 대기 (league `Player`, market 현재가(MKT-04·05), order 체결 이벤트(ORD-03) 필요)

## 1. 조회 경로

| 경로 | 용도 |
|---|---|
| REST `GET /api/leagues/{leagueId}/assets/me` | 화면 첫 진입, 새로고침, 재접속 시 한 번 조회 |
| 웹소켓 `/topic/leagues/{leagueId}/players/{playerId}/assets` | 화면을 보는 동안 변동 반영 |

- 두 경로 모두 `AssetQueryService.getPlayerAsset`을 써서 계산 로직은 하나다. 계산은 항상 서버에서 하고 클라이언트는 받은 값을 표시만 한다.
- 본인 확인은 서버가 세션의 `memberId`와 `leagueId`로 league에서 `playerId`를 조회해 한다. 클라이언트가 보낸 `playerId`를 믿지 않는다.
  - REST: 경로에 `playerId`를 받지 않는다 (`me`).
  - 웹소켓: `AssetTopicAuthorizer`가 구독 경로의 `playerId`가 조회한 본인 `playerId`와 같은지 확인한다.

## 2. 발행 시점

자산 평가액은 내 체결이 없어도 바뀐다. 다른 참여자끼리 체결돼도 현재가가 바뀌고, 그 종목을 가진 모든 참여자의 평가액이 달라진다.
반대로 현재가가 그대로이고 내 상태(현금·수량·예약·매입 금액)도 그대로면 자산 값은 바뀌지 않는다.
그래서 매 주기 모든 리그를 다시 계산하지 않고, **값이 바뀔 수 있는 때에만 바뀐 대상에게** 발행한다.

| 변동 원인 | 알려 주는 곳 | 방식 | 대상 |
|---|---|---|---|
| 현재가 변동 (다른 참여자의 체결 포함) | 현재가 캐시 갱신 (3장)이 이전 값과 비교 | 주기 발행: 현재가가 바뀐 종목이 있는 리그만 | 그 리그의 구독자 전원 |
| 내 주문 체결 (현금·수량·매입 금액 변동) | `TradeExecuted` (커밋 이후) | 즉시 발행 | 매수자·매도자만 |
| 내 주문 접수·취소 (예약 자산 변동) | 주문 접수·취소 이벤트 (커밋 이후) | 즉시 발행 | 주문한 플레이어만 |
| 미체결 만료 (09:00), 리그 종료 (예약 해제) | `TradingDayChanged` 이후 만료 처리, 리그 종료 이벤트 (커밋 이후) | 즉시 발행 | 그 리그의 구독자 전원 |

- 구독자가 없는 토픽은 계산하지 않는다 (`TopicSubscriptions`).
- 리그 단위 발행은 구독 경로를 리그별로 묶어 `AssetQueryService.getPlayerAssets(leagueId, playerIds)`를 리그당 한 번 호출한다.
  - 자산이 없는 플레이어(리그 시작 전 등)는 결과에서 빠지므로 발행하지 않는다.
- 즉시 발행(매수자·매도자)은 `getPlayerAssets`로 두 명을 함께 조회한다.
- 현재가도 내 상태도 바뀌지 않은 리그는 계산·조회·발행을 모두 하지 않는다. 계산량은 리그 수가 아니라 거래가 일어나는 리그 수에 비례한다.
- 예외는 리그 단위로 잡는다. 한 리그의 실패(현재가 없음 등)를 잡지 않으면 그 주기의 다른 리그 발행까지 모두 빠진다.

### 2.1. 변경 리그를 체결 이벤트로 표시하지 않는 이유

체결 이벤트로 리그에 "변경됨" 표시를 하면, 현재가 캐시가 갱신되기 전에 주기 발행이 돌아 이전 현재가로 발행하고 표시를 지울 수 있다.
그 뒤 캐시가 새 현재가로 바뀌어도 표시가 없어 다음 체결 전까지 화면에 반영되지 않는다.
현재가는 캐시 갱신 때만 바뀌므로 "현재가가 바뀐 리그"는 캐시 갱신이 정한다.

## 3. 현재가 캐시

현재가는 체결될 때만 바뀌고 자산·종목·호가창 화면과 REST 조회가 모두 읽는다. 화면마다 리그별로 DB를 읽지 않도록 market이 현재가를 메모리에 캐시한다.
자산 계산에 종목 이름·상장자(자사주 판단)도 함께 필요하므로, 현재가만이 아니라 진행 중인 리그의 종목 표시 정보(`StockSnapshot`: 이름·소개·상장자·현재가)를 통째로 캐시한다.

| 항목 | 내용 |
|---|---|
| 원본 | DB `stock.current_price`. 체결 트랜잭션 안에서 market이 `TradeExecuted`를 동기 구독해 갱신한다 |
| 캐시 갱신 | 1초마다(`naspi.market.current-price.refresh-interval`, 기본 1s) 진행 중(`STARTED`) 리그의 `stock`을 한 쿼리로 읽어 캐시를 덮어쓴다. **캐시에 쓰는 곳은 이 갱신 하나뿐이다** (`CurrentPriceRefreshService`, 전용 스레드 하나로 실행하는 `CurrentPriceRefreshScheduler`) |
| 변경 감지 | 덮어쓸 때 이전 값과 비교해 현재가가 바뀐 종목이 있는 리그 ID를 모아 `CurrentPricesChanged`로 알린다 (websocket이 구독해 2장의 주기 발행을 한다). 새로 캐시에 들어온 리그(리그 시작, 서버 재시작 직후)도 바뀐 것으로 본다. 이름·소개만 바뀐 경우는 알리지 않는다 |
| 캐시에 없을 때 | 대기실·종료 리그나 첫 갱신 전에는 `StockQueryService.findAllByLeagueId`가 DB에서 읽는다. 종료된 리그는 다음 갱신에서 캐시에서 빠진다 |
| 사용처 | 화면 표시용 조회만 (`StockQueryService.findAllByLeagueId` → 자산 조회, 리그 상세, 이후 종목·호가창 토픽) |
| 위치 | market. 인터페이스 `StockSnapshotCache`는 `domain`, 로컬 메모리 구현 `LocalStockSnapshotCache`는 `infra`. 다중 서버 시 Redis 구현으로 교체한다 |

- 쓰는 곳이 하나라서 늦게 도착한 옛날 값이 최신 값을 덮어쓰는 경쟁이 없다. 순번(버전) 컬럼이 필요 없다.
  - 체결 직후에도 캐시를 갱신하는 경로를 추가하면 쓰는 곳이 둘이 되어 이 경쟁이 생긴다. 그때는 `stock`에 순번을 함께 저장하고 순번이 더 클 때만 덮어써야 한다.
- DB는 항상 캐시보다 같거나 최신이다 (DB 커밋 → 캐시 갱신 순서). 캐시는 최대 갱신 주기만큼 늦을 수 있다.
- 리그 시작 시 시초가 적용(MKT-04)도 DB에 반영되면 다음 갱신 때 캐시에 들어간다.
- 진행 중인 리그의 종목 소개 수정도 최대 갱신 주기만큼 늦게 보인다 (표시용이라 허용).
- 캐시를 원본으로 두고 DB에 나중에 쓰는 방식(write-back)은 쓰지 않는다. 체결 트랜잭션이 어차피 DB에 쓰므로 얻는 것이 없고, 장애 시 현금·수량과 현재가가 어긋난다.

## 4. 값 일관성

두 방식 모두 현금·보유 수량·예약·매입 금액은 DB에서, 현재가는 캐시에서 읽어 **매번 처음부터 다시 계산**한다.
이전 메시지 값에 변동분을 더하는 누적 방식을 쓰지 않는다. 그래서 즉시 발행된 플레이어를 주기 발행이 다시 계산해도 같은 상태라면 같은 값이 나오고, 그 사이 현재가가 바뀌었다면 바뀐 값이 새로운 정답이다.

반영 지연: 현재가 변동은 최대 약 1초 (캐시 갱신 주기), 내 상태 변동은 커밋 직후.

## 5. 주의 사항

### 5.1. 즉시 발행은 커밋 이후에 한다

- 즉시 발행 리스너는 `@TransactionalEventListener(phase = AFTER_COMMIT)`로 둔다.
- 커밋 전에 조회하면 반영 전의 값을 "즉시" 발행하게 된다.
- 발행 실패가 원래 트랜잭션을 되돌리면 안 되므로, 발행 예외는 리스너 안에서 기록만 하고 삼킨다. 주기 보정이 없으므로 다음 변동이나 재접속 시 REST 조회(5.4)까지 이전 값이 남는다.
- 참고: 초기 자산 배분(`LeagueStartedListener`)과 market의 현재가 DB 갱신은 반대로 같은 트랜잭션 안에서 동기로 처리해야 한다. 원자성이 필요한 처리와 화면 발행을 구분한다.

### 5.2. 즉시 발행도 현재가는 캐시 값을 쓴다

- 즉시 발행에 방금 체결된 가격(DB 값)을 쓰면, 직후 주기 발행이 아직 갱신 전인 캐시 값으로 계산해 화면 현재가가 10,500 → 10,000 → 10,500처럼 되돌아갈 수 있다.
- 그래서 즉시 발행도 캐시의 현재가를 쓴다. 매수자·매도자가 바로 알아야 하는 현금·수량·예약·매입 금액은 DB에서 읽으므로 즉시 반영되고, 현재가와 평가액은 다음 캐시 갱신 후 주기 발행으로 따라온다.
- 캐시를 쓰는 곳이 하나라 화면의 현재가는 시간 순으로만 바뀌고 되돌아가지 않는다.

### 5.3. 메시지 순서가 뒤집힐 수 있다

주기 발행 계산과 즉시 발행이 겹치면 화면이 잠깐 이전 값으로 돌아갈 수 있다.

1. 주기 발행이 체결 전 DB를 읽기 시작한다.
2. 체결이 커밋되고 즉시 발행이 먼저 나간다 → 화면에 새 값.
3. 1번 계산이 늦게 끝나 발행된다 → 화면이 **체결 전 값으로 되돌아감**.
4. 변경 리그만 주기 발행하므로 다음 변동이 없으면 이 값이 남는다.

대응:
- 메시지에 계산 시각(DB 조회 시점, 주입받은 `Clock` 기준)을 담는다.
  - 기존 `TopicEnvelope.publishedAt`은 **발행 시각**이라 쓸 수 없다. 3번 단계의 늦은 메시지는 계산은 먼저 했지만 발행이 늦어 `publishedAt`이 더 최근이 되기 때문이다.
  - 자산 메시지(`AssetResponse`)에 계산 시각 필드(예: `asOf`)를 추가한다.
- 클라이언트는 표시 중인 값보다 계산 시각이 이른 메시지를 무시한다. 프론트와 이 규칙을 합의한다.
- 3번의 늦은 메시지를 무시하면 2번의 새 값이 유지되므로 4번 문제도 생기지 않는다.

### 5.4. 재접속

웹소켓이 끊겼다 다시 연결되면 그 사이 변동을 받지 못한다. 변경이 있을 때만 발행하므로 다음 메시지가 한참 오지 않을 수 있다. 재구독 시 REST로 한 번 다시 조회한다.

### 5.5. 현재가 캐시는 표시용이다

- 주문·체결·정산 등 거래 로직은 캐시를 읽지 않는다. 정책상 거래 판단에는 현재가가 쓰이지 않는다 (가격제한폭은 기준가, 시장가 보호 범위는 최우선 상대 호가, 체결 가격은 대기 주문 가격).
- 거래 로직에 현재가가 필요해지면 DB 값을 읽는다.

### 5.6. 단일 서버 전제

로컬 메모리 캐시는 서버마다 따로 가지므로 단일 서버 전제다 (내장 브로커와 같은 전제). 다중 서버로 갈 때 `TopicMessagePublisher`의 Redis Pub/Sub 교체와 함께 캐시도 Redis 구현으로 옮긴다.
Redis로 옮기면 네트워크 실패로 캐시 갱신이 빠질 수 있다. 쓰는 곳은 여전히 주기 갱신 하나이므로 다음 주기에 다시 맞춰진다.
