### ORD-03 접수된 주문은 가격·시간 우선 원칙에 따라 상대 주문과 체결된다
- Jira: ND-36, ND-74
- 정책: [order.md#체결](../../policies/v1/domain/order.md#체결)
- 선행: ORD-01, AST-05
- 내용: 체결 시 정산(AST-05) 후 `TradeExecuted` 이벤트 발행
- 완료 조건
  - [X] 매수 가격 ≥ 매도 가격일 때 체결
  - [X] 매수는 높은 가격, 매도는 낮은 가격 우선, 같은 가격은 먼저 접수된 주문 우선
  - [X] 체결가 = 먼저 대기 중이던 주문의 가격
  - [X] 부분 체결 지원
  - [X] 체결 1건마다 체결 기록(매수·매도 주문, 종목, 거래일, 가격, 수량, 금액, 일시)을 정산과 같은 트랜잭션에서 저장하고, 수정·삭제하지 않으며 회원을 참조하지 않는다 (ND-74)
  - [X] 종목별·거래일별 체결 수량·금액 합계와, 종료 시각에 가까운 체결부터 500주까지의 조회를 제공한다 (리그 종료 VWAP용. 거래량 표시는 market `stock_daily_price`)
- 비고 (asset 구현 시 전달받은 주의사항): 정산 락 순서는 `settle` 한 번 안에서만 보장된다. 접수 때 잡은 예약 락, 한 주문이 여러 상대와 체결될 때의 이전 정산 락과 섞이면 데드락이 가능하므로 리그 단위로 매칭을 직렬화한다.
- 결정: 직렬화는 DB 락으로 한다 (pod가 여러 개여도 동작해야 하므로 JVM 락 불가). 접수·취소 트랜잭션 시작 때 league 행을 `SELECT ... FOR UPDATE`(비관적 락)로 잠근 뒤 호가창 조회, 주문 save, 매칭, 정산을 같은 트랜잭션에서 처리한다.
  - 시간 우선순위는 주문 `id` 순서이므로 save는 반드시 락을 잡은 뒤에 한다 (락 밖에서 save하면 id 순서와 처리 순서가 어긋난다)
  - 락 순서는 리그 락 → asset 락(예약·정산)으로 고정한다
  - 리그 단위인 이유: 호가창은 종목별이지만 현금은 플레이어 단위라 종목별로 쪼개면 asset 락과 데드락 위험이 생긴다
  - league 행 락은 league 모듈이 메서드로 노출한다 (order가 league 하위 모듈이므로 Service 호출 가능)
- 결정: `TradeExecuted`는 `order/application`에 두고 order가 발행한다. market은 이 이벤트를 `market/application`의 UseCase로 구독한다 (UseCase는 하위 모듈 참조 가능). README 이벤트 표(order 발행, market·websocket 구독)와 같다.
- 리뷰 포인트: market UseCase가 order의 이벤트 클래스를 import하므로 order → market(서비스 호출)과 market → order(이벤트) 패키지 순환이 생긴다. 대안은 order가 체결 후 market 서비스를 직접 호출하는 방식(순환 없음, 문서의 market 구독 설명 수정 필요)이다. 팀 리뷰에서 확정한다.

### ORD-05 참여자는 수량만 지정해 최우선 호가 기준 5% 이내에서 즉시 체결되는 시장가 주문을 넣을 수 있다
- Jira: ND-38
- 정책: [order.md#주문](../../policies/v1/domain/order.md#주문)
- 선행: ORD-03, AST-03
- 완료 조건
  - [x] 매수: 최우선 매도 호가 × 1.05, 매도: 최우선 매수 호가 × 0.95를 계산한 뒤 100원 미만 절사
  - [x] 산정한 보호 가격이 당일 상·하한가를 벗어나면 해당 상·하한가 적용
  - [x] 보호 범위는 접수 시 확정, 이후 호가 변동은 반영하지 않음
  - [x] 범위 내 체결 후 잔량 취소, 체결 가능 수량 0이면 전량 취소
  - [x] 매수 시 보호최고가 × 주문 수량을 현금 예약 (`AssetReservationService.reserveCashForBuy`, AST-03). 주문에 예약 기준 가격(보호최고가)을 남겨 취소·정산에 사용
- 결정: 시장가 매수 현금은 보호최고가 × 주문 수량으로 예약한다. asset의 예약·해제·정산이 예약 기준 가격 × 수량 단위라 정책서의 "상대 호가 순차 합산, 부족분은 보호최고가" 계산을 담을 수 없어서 asset을 바꾸지 않는 방식으로 정했다. 체결·취소 후 남은 예약금은 전액 해제하므로 최종 자산은 정책서와 같고, 접수 직후 예약금이 정책서보다 커서 주문 가능 현금이 일시적으로 더 줄어든다.
- 비고: 정책서와 다름 (구현은 보호최고가 × 주문 수량 예약). asset 금액 단위 예약 API 추가는 후속 작업. 정책서 5.3 문구(합산 방식)와 구현이 다르다. 팀에서 정책서를 구현에 맞출지 asset에 금액 단위 예약 API를 추가할지 정해지면 이 항목을 갱신한다.
- 결정: 상대 호가가 없으면 주문을 저장하고 `CANCELED`/`MARKET_NOT_FILLED`로 전량 취소하며 자산은 예약하지 않는다. 응답에 취소 사유는 넣지 않는다 (ORD-08 상세 조회로 확인). 상·하한가는 market `StockQueryService#getDailyPriceLimit`로 조회한다 (MKT-06)

### ORD-06 주문과 취소가 동시에 몰려도 체결 순서와 자산 정합성이 보장된다
- Jira: ND-39
- 정책: [asset.md#주문-가능-자산-및-정산](../../policies/v1/domain/asset.md#주문-가능-자산-및-정산)
- 선행: ORD-03
- 완료 조건
  - [X] 종목별 매칭을 직렬화하여 체결 순서 보장 (리그 단위로 직렬화하므로 종목별보다 강하게 보장)
  - [X] 취소와 체결이 동시에 요청되면 먼저 확정된 처리 결과 적용
  - [X] 동시 주문으로 예약 자산이 초과 사용되지 않음 (동시성 테스트)
- 결정: 직렬화 방식은 리그 행 DB 락 ([ORD-03](#ord-03-접수된-주문은-가격시간-우선-원칙에-따라-상대-주문과-체결된다) 비고 참고). 종목별이 아닌 리그 단위로 직렬화한다
- 진행: 접수와 취소가 모두 `LeagueTradingService.lockForTrading`을 먼저 잡아 같은 리그의 처리가 차례로 진행된다. 취소는 락을 잡은 뒤 주문을 읽으므로 먼저 커밋된 체결이 반영된 상태를 보고, 이미 체결 완료된 주문이면 상태 오류(`502`)로 거절된다. `LimitOrderConcurrencyTest`가 동시 매수 예약 초과, 같은 주문 동시 취소, 취소·체결 경합, 여러 참여자의 주문·취소 혼합(현금·주식 총량 보존, 예약 = 미체결 주문 잔량)을 검증한다. 접수 순서대로 하나씩 처리하면 같은 가격에서 먼저 접수된 주문부터 전량 체결되고 호가창이 교차하지 않는다는 점은 `OrderMatcherTest#sequentialArrivalKeepsTimePriority`가 검증한다.

### ORD-07 참여자는 자신의 미체결 주문을 취소할 수 있다
- Jira: ND-40, ND-72
- 정책: [order.md#미체결-주문-관리](../../policies/v1/domain/order.md#미체결-주문-관리)
- 선행: ORD-02, AST-06
- 완료 조건
  - [X] 본인 주문의 미체결 잔량만 취소, 예약 자산 해제
  - [X] 가격·수량 변경은 취소 후 신규 주문으로 처리 (새 접수 시각 기준)
- 진행: `POST /api/leagues/{leagueId}/orders/{orderId}/cancel`(`OrderCancelController`) → `LimitOrderService.cancelOrder`. 리그 락 → 주문 행 락(`findWithLockById`) → 취소 → 잔량 예약 해제 순서다. 없는 주문·다른 리그 주문·남의 주문은 모두 `ORDER_NOT_FOUND`(`504`)로 응답해 남의 주문 존재 여부를 알리지 않는다. 체결 완료·취소·만료된 주문은 `INVALID_ORDER_STATUS_TRANSITION`(`502`).
- 결정 (ND-72, PM 확인): 별도 주문 변경(정정) 기능은 두지 않는다. 사용자가 가격·수량을 바꾸려면 취소 API로 기존 주문을 취소한 뒤 지정가 주문 API로 새 주문을 넣는다. 새 주문은 새 접수 시각으로 시간 우선순위가 정해지므로 정책서 §5.6 "변경"과 같다.
- 진행 (취소 사유): 취소 시 사유 `USER_REQUESTED`와 취소 일시(리그 락 뒤 거래 가능 판정 시각) 기록.
- 비고 (asset 구현 시 전달받은 주의사항): asset은 플레이어별 예약 합계만 알므로 같은 주문의 예약을 두 번 해제하지 않도록, order가 주문 행 락으로 상태 전환을 한 번만 처리한다.

  - [x] 취소 내역: 취소가 발생한 경우 취소 수량, 취소 일시, 취소 사유를 제공한다. 거래일 변경으로 만료된 잔여 수량은 취소 수량에 합산한다
  - [x] 취소 사유는 코드로 제공하고 표시 문구는 클라이언트가 매핑한다: 사용자 직접 취소("직접 취소"), 시장가 일부 체결 후 잔량 취소("체결 가능 수량 부족"), 시장가 체결 없이 전량 취소("체결 가능 수량 없음"), 자전거래 방지("내 주문 간 체결 방지", ORD-04), 거래일 변경 만료("거래일 변경으로 만료", ORD-09)
  - [x] 대기 내역: 미체결 잔여 수량이 대기 중이면 현재 대기 수량(`최초 주문 수량 - 체결 수량 - 취소 수량`)을 제공하고, 없으면 제공하지 않는다
  - [ ] 접수·체결·취소 처리 중에도 확정된 상태만 조회되고 중간 상태는 노출하지 않는다 (ORD-06). 상대방 회원이 탈퇴해도 본인의 체결 내역 조회에 영향이 없다
  - 진행: 구현 완료(`OrderQueryService`, `REPEATABLE_READ`)와 상대방 탈퇴 테스트(`OrderQueryServiceTest#counterpartyWithdrawn`)는 있다. 중간 상태 미노출은 H2와 PostgreSQL의 격리 동작이 달라 PostgreSQL(Testcontainers)에서 검증하는 후속 Task로 분리한다 (Jira 발급 후 기재)
- 결정: 취소 일시·사유는 `orders`에 컬럼으로 저장한다 (`취소일시`, `취소사유`, ERD 반영 완료). 취소 일시·사유 기록은 취소·만료·시장가 잔량 취소·자전거래 취소 처리에서 함께 채운다. 기록 구현 완료 (`Order.canceledAt`, `Order.cancelReason`, `CancelReason`)
- 결정 (확정)
  - 체결 일시가 같은지는 저장값 그대로 비교하고 응답 일시도 저장값 그대로 내린다 (한 번의 매칭에서 나온 체결은 같은 체결 일시를 가진다)
  - 주문 정정은 별도 기능이 없다 (ND-72). 취소 → 신규 접수로 처리하며 취소 사유는 `USER_REQUESTED`다
  - 응답의 취소 사유는 5종(`USER_REQUESTED`, `MARKET_PARTIALLY_FILLED`, `MARKET_NOT_FILLED`, `SELF_TRADE_PREVENTED`, `TRADING_DAY_EXPIRED`)만 문서화한다. `LEAGUE_ENDED`, `MEMBER_WITHDRAWN`은 ORD-10/11에서 추가한다
  - 체결 내역은 체결 일시 오름차순(오래된 것 먼저)이다

### ORD-09 지정가 주문의 미체결 잔량은 다음 거래일 09:00에 자동으로 만료된다
- Jira: ND-42
- 정책: [order.md#미체결-주문-관리](../../policies/v1/domain/order.md#미체결-주문-관리)
- 선행: LEA-11, AST-06
- 완료 조건
  - [ ] 거래일 전환 UseCase(LEA-11 `TradingDayChangeUseCase`) 호출 시 이전 거래일 지정가 미체결 잔량 만료, 예약 자산 해제
  - [ ] 이미 체결된 부분 유지
- 결정: 09:00 이후 전환 처리 전 신규 주문은 접수 거절한다(방식 A, MKT-06에서 구현, `213`). 남은 일은 전환 UseCase에서 만료 호출
- 진행: `Order.expire(LocalDateTime)`가 사유 `TRADING_DAY_EXPIRED`와 일시를 기록한다. 인자는 거래일 전환 시각(09:00:00 KST)을 넘긴다.
- 비고 (asset 구현 시 전달받은 주의사항): 해제 중 데이터 오류가 나면 트랜잭션 전체가 롤백되므로, 만료 일괄 처리는 리그 단위 한 트랜잭션으로 처리한다 (리그 락 안에서 끝내 순서를 보장하고, 오류 시 그 리그의 전환이 함께 롤백되어 다음 실행에서 보정된다).
- 확인 필요 (ORD-10, ORD-11 포함): 지금은 주문 상태를 바꾸는 경로(접수·체결, 취소)가 모두 리그 락 안에서 실행되고, `LimitOrderService.cancelOrder`의 주문 행 락(`findWithLockById`)은 리그 락과 겹치는 방어적 중복이다(리그 락만으로도 `LimitOrderConcurrencyTest` 40/40 통과, 2026-11-19 대조 실험). 만료·종료·탈퇴 취소가 리그 락을 잡지 않고 주문 상태를 바꾸는 경로가 된다면(예: 위 비고처럼 주문별로 트랜잭션을 나눈 만료 배치) 사용자 취소와 같은 주문을 동시에 처리해도 예약이 두 번 풀리지 않는지(주문 행 락의 필요성)를 동시성 테스트로 확인한다. 리그 락 안에서 처리한다면 주문 행 락을 유지할지 제거할지 이때 결정한다.
